# Design: Add the N=16384 column to both overhead tables

Date: 2026-06-05
Status: Approved design (pending spec review)
Builds on: `2026-06-04-overhead-burst-window-and-flowtable-delay-design.md` (drivers, delay model, log slimming all already in place).

## 1. Goal

Add a 16384-concurrent-flow column to:
- `overhead.md` table 2 — the LPCC switch-buffer / flow-table-memory table (currently 64,256,1024,4096).
- `overhead-maint.md` — the DCQCN maintenance-overhead table (currently 64,256,1024,4096).

Keep the existing 64–4096 columns; only run the new 16384 point and rebuild each table over all five columns.

## 2. Key constraint (why 16384 is special)

The fabric is a DCI topology whose bottleneck is a 100 Gbps, ~10 ms-RTT long-haul chain (node 74 → 75 → 76 → 77 → 78, 1.25 ms/hop). Per-link serialization sets a hard floor on how long flows take to drain:

- **Buffer table (1 MB flows):** the table reports *peaks* (peak buffer, flow-table memory, flow count), which are reached at the burst (~0.13–0.15 s) and are independent of `SIMULATOR_STOP_TIME` as long as SIM > ~0.15 s. So 16384 only needs to simulate just past the peak.
- **Maintenance table (256 KB flows):** needs flows to *complete* for meaningful FCT. 16384 × 256 KB = 4 GB; serialization through the 100 G bottleneck ≈ 0.33 s, plus 0.12–0.13 s start + queueing ⇒ last flow finishes ≈ 0.5 s. So SIM 0.35 s (used for 64–4096) is too short; 16384 needs a longer window.

## 3. Decisions (from brainstorming)

| # | Decision |
|---|----------|
| Buffer 16384 | Run at the current buffer settings: **1 MB flows, max-over-switches, SIM 0.18 s**. Peaks are SIM-independent, so this is directly comparable to the existing 64–4096 (which were captured under SIM 0.35; peaks identical). |
| Maintenance 16384 | Run at **256 KB flows, SIM 0.6 s**, raised per-run timeout, on-arm delay 20/50 ns, off-arm 0/0. Completed-flow FCT and active-sample goodput are SIM-independent, so 16384-at-SIM-0.6 is comparable to 64–4096-at-SIM-0.35. |
| Reuse existing dumps | Do **not** re-run 64–4096. Their dumps exist (verified): `dump_burst_overhead/lpcc/{64,256,1024,4096}` (1 MB) and `dump_burst_overhead_ab/{on,off}/{64,256,1024,4096}` (256 KB). |
| Rebuild over all columns | After running 16384, rebuild each table with `--counts 64,256,1024,4096,16384` (the analyzer reads all per-N dumps). |
| Script reproducibility | Update both drivers so a full run reproduces all five columns: per-N SIM rule, default COUNTS incl 16384, larger timeout; plus a **decoupled table-count list** so a subset run still rebuilds the full-column table. |
| Footnotes | Note that 16384 used a different SIM (buffer 0.18 same as the rest; maintenance 0.6 vs 0.35) and — if 16384 maintenance does not fully complete within SIM 0.6 — annotate the column as partial/indicative. |
| Order | Run buffer 16384 first (lighter, SIM 0.18), then maintenance 16384 (heaviest, SIM 0.6). Background + 10-min progress reports. |
| Commit | Results remain uncommitted unless the user asks (consistent with prior turns). |

## 4. Design A — buffer 16384 (`run-overhead-buffer.sh` + rebuild)

The buffer driver already defaults `COUNTS=64,256,1024,4096,16384` and `SIM_STOP=0.18`, discards stdout, monitors node 74, `--RngRun=1`. Two needs:

1. **Run only 16384** without clobbering the existing 64–4096 dumps and without producing a 16384-only table. Introduce a decoupled table-count list:
   - `COUNTS` (env) — which N to *simulate* (set `COUNTS=16384` for this pass).
   - `TABLE_COUNTS="${TABLE_COUNTS:-64,256,1024,4096,16384}"` — which N the final `analyze-overhead.py` renders. The driver's final analyzer call uses `TABLE_COUNTS`, not `COUNTS`.
   With `COUNTS=16384 TABLE_COUNTS=64,256,1024,4096,16384`, the driver runs only the 16384 sim, then rebuilds the table over all five (existing 64–4096 dumps + the new 16384 dump).

2. **Restore `overhead.md` first.** Before appending, drop the previously-appended buffer section (everything from the `<!-- generated by run-overhead-buffer.sh ... -->` comment to EOF), keeping only the original maintenance table, so a single clean 5-column buffer table is appended.

Provenance/footnote: `counts=64,256,1024,4096,16384 | flows=uniform bytes=1000000 start[0.12,0.13] SIM=0.18 RngRun=1`.

Feasibility: 16384 incast is event-heavy, but SIM 0.18 s caps it and the peaks land at ~0.13–0.15 s, so even a slow or timeout-truncated 16384 run yields valid peaks. `flow_table.txt` is written every 100 µs throughout.

## 5. Design B — maintenance 16384 (`script-ab-maintenance.sh` + rebuild)

The maintenance driver currently has flat `SIM_STOP=0.35`, 256 KB flows, per-arm delay keys, filtered stdout, `PER_RUN_TIMEOUT=3600`. Changes:

1. **Per-N SIM rule:** `SIM_STOP = (N >= 16384) ? 0.6 : 0.35`.
2. **Larger timeout for big N:** `PER_RUN_TIMEOUT="${PER_RUN_TIMEOUT:-3600}"` overridable; for this pass run 16384 with a larger value (e.g. `PER_RUN_TIMEOUT=14400`, 4 h).
3. **Decoupled table counts:** add `TABLE_COUNTS="${TABLE_COUNTS:-64,256,1024,4096,16384}"`; the final analyzer call uses `TABLE_COUNTS`. Default `COUNTS` stays `64,256,1024,4096,16384` for full reproducibility, but this pass runs `COUNTS=16384`.
4. **Provenance/footnote:** `counts=64,256,1024,4096,16384 | flows=uniform bytes=256000 start[0.12,0.13] SIM=0.35(64-4096)/0.6(16384) RngRun=1 | on-arm FLOW_TABLE_OP_DELAY 20-50ns`. Add a note: "N=16384 simulated with SIM 0.6 s (vs 0.35 s for ≤4096) so 4 GB can drain the 100 G DCI link; if fewer than ~90% of 16384 flows completed, treat the 16384 column as indicative."

For this pass: `COUNTS=16384 PER_RUN_TIMEOUT=14400 TABLE_COUNTS=64,256,1024,4096,16384 bash script-ab-maintenance.sh` runs DCQCN on/off for 16384 (256 KB, SIM 0.6), then rebuilds the table over all five columns from existing + new dumps.

Risk: even at SIM 0.6 s, 16384/256 KB may not fully complete and the run may take hours or hit the timeout. The analyzer renders whatever completed; the footnote + a completed-flow check (fct line count vs 16384) decide whether to mark it indicative.

## 6. Architecture / data flow

```
gen-sweep-flows (16384 only) ─┐
                              ├─> binary (16384 on/off or lpcc) ─> dump/<...>/16384/{flow_table,fct,run.log|err}
existing 64-4096 dumps ───────┘
                              └─> analyze-overhead.py --counts 64..16384 ─> overhead.md (buffer) / overhead-maint.md
```

No analyzer change (it already renders an arbitrary `--counts`). No C++ change. Only the two drivers gain `TABLE_COUNTS` + the maintenance per-N SIM rule + timeout override.

## 7. Implementation-time verifications

1. Existing 64–4096 dumps still present at run time (verified now; re-check before rebuild). If absent, the affected N must be re-run.
2. After the maintenance 16384 run, check `wc -l dump_burst_overhead_ab/{on,off}/16384/fct.txt`; if « 16384 (timeout-truncated), mark the column indicative in the footnote.
3. `TABLE_COUNTS` is used only by the final analyzer call, not by the per-N simulation loop.
4. Buffer `overhead.md` restored to the original 6-line maintenance table before the (single) buffer-table append, to avoid duplicate sections.

## 8. Testing / verification

- **Driver syntax:** `bash -n` both scripts.
- **Decoupling smoke (cheap):** with NO new sim, run the analyzer rebuild step alone over existing dumps with `--counts 64,256,1024,4096` and confirm it reproduces the current tables (sanity that the rebuild path is correct) before adding 16384.
- **Buffer 16384:** after the run, `overhead.md` shows a 5-column buffer table; the 16384 cells are numeric (peak buffer likely 128 MB / 100 %, peak flows ~ the N-scaled value); original maintenance table still at top; no multi-GB `run.log` (stdout discarded).
- **Maintenance 16384:** after the run, `overhead-maint.md` shows 5 columns; report 16384 on/off completed-flow counts; if ~complete, On vs Off should show an even larger divergence than at 4096; if truncated, footnote marks it indicative.
- **Isolation:** `dump_*`/`sweep_*` stay gitignored (no committed data).
